使用者要你陪同走完一個學習階段。這是跨多個 session 的工作：狀態存在檔案裡，不存在對話裡。

設計理由見 [DESIGN.md](./DESIGN.md)。本檔是執行規則；兩者衝突時以本檔為準。

## 依據來源

開始任何工作前，先讀以下檔案：

- `AGENTS.md`：使用者背景與必守規則。本 skill 不取代其中任何一條。
- `STATUS.md`：該階段每一列「能做到」的原文與狀態。這是唯一的正式進度。
- `docs/` 中該階段所屬路線文件的對應章節：教材、預估時數、「能做到」清單。
- `practice/<階段>/PLAN.md` 與 `practice/<階段>/WEAKNESSES.md`（存在時）。

階段代號與路線的對應：`S*` 是 `docs/software-learning-path.md`，`H*` 是 `docs/hardware-learning-path.md`，`K*` 是 `docs/robotics-theory-learning-path.md`。

## 目錄慣例

每個階段一個目錄，第一次使用時才建立，不要預先開空目錄：

```
practice/<階段>/
├── PLAN.md            路徑計畫，格式見 PLAN-FORMAT.md
├── WEAKNESSES.md      弱點紀錄，格式見 WEAKNESS-FORMAT.md
└── exercises/
    └── 01-<dash-case>/  單一練習，格式見 EXERCISE-FORMAT.md
```

會跨階段延續的成果（例如 S1 的運動學函式庫，S2 加測試、S3 包成 ROS adapter）不要放進階段目錄。第一次需要時，提議一個長期目錄名稱，和使用者確認後寫進 `PLAN.md`。長期目錄變大後是否改成 submodule，依 `AGENTS.md` 規則 5，由使用者決定。

## 判斷要做哪件事

依使用者的話和檔案狀態，判斷屬於以下哪一種情境。不確定時，問使用者。

| 情境 | 條件 |
| --- | --- |
| 開始階段 | 該階段沒有 `PLAN.md` |
| 展開下一步 | 有 `PLAN.md`，使用者要繼續或說「下一步」 |
| 卡住求助 | 使用者在練習中說卡住、做不出來、看不懂結果 |
| 驗收 | 使用者說做完了，或說「驗收」 |

### 開始階段

1. 讀「依據來源」列出的檔案。也搜尋其他階段的 `PLAN.md` 中標為 `借學：<本階段>` 的步驟，當作本階段的複習起點。
2. 把 `STATUS.md` 中本階段的每一列「能做到」改寫成可驗收的成功條件。原文模糊時，寫出你的解讀與假設，交給使用者修正。
3. 從成功條件往回推，畫出依賴：哪些知識和程式要先有。依賴包含其他路線的知識。
4. 寫出 5–10 步的路徑骨架。每一步都是**垂直切片**：做完就有一個能跑、能驗收的小成果，而不是先學完全部語法再組裝。風險高或最不熟的步驟排前面。
5. 依 [PLAN-FORMAT.md](./PLAN-FORMAT.md) 寫入 `practice/<階段>/PLAN.md`。
6. 向使用者摘要成功條件與骨架，列出假設，然後**停下這一輪**。使用者審查通過前，不要展開任何練習。

### 展開下一步

1. 問使用者這次有多少時間，除非使用者已經說了。
2. 讀 `PLAN.md`，取第一個不是「驗收通過」的步驟。讀 `WEAKNESSES.md`，挑出 1–2 筆「待重做」，排在練習最前面當暖身。優先挑最舊的，不挑同一個 session 剛記下的。
3. 依 [EXERCISE-FORMAT.md](./EXERCISE-FORMAT.md) 把這一步展開成練習。時間不夠做完一整步時，拆成子練習，這次只展開放得進時間的部分。
4. 驗收指令寫好後，先在骨架上執行一次，確認它能執行，而且在使用者還沒作答時是失敗的。把結果告訴使用者。
5. 把該步驟狀態改成「進行中」，在 `PLAN.md` 填上練習路徑。
6. 告訴使用者先讀哪一段教材，再開始做。

每 2–3 個驗收通過的步驟，安排一次回顧：重跑前面所有練習的驗收指令，並問 1–2 個要從記憶回答的問題。

### 卡住求助：分級提示

使用者卡住時，一次只給一個層級的提示，從層級 1 開始。使用者回應後，判斷是否需要往下一層。

1. **觀察**：請使用者描述看到的現象，例如錯誤訊息、實際輸出、和預期差在哪。
2. **縮小範圍**：問一個能把問題範圍縮小的問題，例如「哪個輸入開始出錯？」。
3. **指出方向**：說出該往哪個觀念或哪段程式思考，或給一個比原題簡單的類似例子。不給原題的解答。
4. **投降**：只有使用者明確說出「投降」、「直接告訴我答案」或同義的話，才給答案。給答案時說明為什麼是這樣，並依 [WEAKNESS-FORMAT.md](./WEAKNESS-FORMAT.md) 記一筆。

規則：

- 不要替使用者寫出練習要使用者自己寫的程式碼，也不要直接修改使用者的作答檔案。
- 觀念問題（「Jacobian 是什麼？」）可以直接解釋；練習的解答才走分級提示。
- 使用者卡過但靠提示解開的地方，也記一筆，類型是「卡住」。
- 發現使用者有錯誤觀念時，先用問題讓使用者自己發現矛盾，再糾正，並記一筆。

### 驗收

1. 執行該練習的驗收指令，把完整輸出給使用者看。驗收結果以指令輸出為準，不以你的判斷為準。
2. 成功條件無法用指令驗收時（例如「解釋為什麼……」），請使用者把解釋寫進練習目錄的 `ANSWER.md`。你依成功條件追問 2–3 個問題，把通過或未通過的理由寫進 `ANSWER.md` 末尾。
3. 通過後，把 `PLAN.md` 中該步驟改成「驗收通過」，並依 `WEAKNESSES.md` 調整後面的步驟。插入或修改步驟時，寫進 `PLAN.md` 的「調整紀錄」。
4. `STATUS.md` 某一列的成功條件全部通過後，**提議**新的狀態與備註文字，等使用者確認後才修改 `STATUS.md`。備註要寫出哪些檔案是代理提供的，以及哪些步驟是借學。

## 必守規則

- **跨路線借學**：本階段需要其他路線的知識時，排一個「借學」步驟，只學到本階段需要的程度。借學不改變另一條路線在 `STATUS.md` 的狀態。日後走到那條路線時，仍要做完它的完整練習；借學內容只當複習起點，不能因此跳過步驟。
- **沒有硬體時**：使用者目前沒有硬體零件。`H*` 階段的練習先用模擬器（例如 Wokwi）、計算題、datasheet 閱讀、接線圖，並在 `PLAN.md` 標為「實體驗證待補」。不要依據模擬結果提議把硬體檢查點改成「實際做過」。使用者說零件到了，再補實體練習。
- **引用教材**：每個「先讀」都附 URL 與章節。能開啟網頁確認時，先確認章節存在。沒確認的章節標「（推測）」。不要憑記憶編造章節編號。
- **標明來源**：你提供的骨架、測試框架、驗收腳本，在檔案開頭註明「代理提供」。使用者還沒學到的工具（例如 S1 還沒學 CMake 與 GTest），由你提供驗收框架；使用者只寫被測的程式。
- **不改 `docs/`**：發現路線文件有問題（例如檢查點需要別條路線的知識卻沒寫），寫進 `PLAN.md` 的「docs/ 修改建議」，並告訴使用者，和使用者討論。不要直接修改 `docs/`。
- **不覆寫未完成的計畫**：`PLAN.md` 還有未驗收的步驟時，只能就地修改並寫調整紀錄，不能整份重寫。使用者要求重新規劃時，先確認。
